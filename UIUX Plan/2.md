# SkoolSys UI/UX Redesign Plan

## 1. Goals

1. **Speed on the daily path.** Taking attendance for a class of about 40 should take under 90 seconds on a phone.
2. **Trust.** Teachers must always know what has been saved, what is pending, and what has synced.
3. **Clarity by role.** Each role should see only what it needs, with no clutter.
4. **Resilience.** The design should work on cheap Android phones, small screens, patchy school Wi-Fi and printed A4.
5. **Consistency.** One design system, with no one-off styles.

## 2. Users and their main jobs

| Role | Top jobs | Device |
|---|---|---|
| Class Teacher | Take daily register, check own class roster, enter marks for own subject | Phone or tablet, often offline, one hand |
| Subject Teacher | Enter marks fast across several classes | Laptop or phone |
| Admin / Principal | Overview of the day, follow up absentees, manage users, print report cards, backup | Desktop |

Design priority: **Attendance > Marks > Students > Admin**, which matches your own module priorities.

## 3. Likely UX problems to check in the current build

These are hypotheses from the README, so verify each against the live app:

- Four P/A/L/E buttons per student can be cramped on small screens, and colour may be the only cue.
- The offline banner may be easy to miss or may disappear, so users won't know what is pending.
- The marks grid may be hard to use on mobile (sticky headers, horizontal scroll).
- Filters, bulk import and the student profile may be dense.
- Admin tools (backup, restore, demo reset) may sit too close to everyday actions, which is a safety risk.
- The 1-click demo login buttons need to be hidden outside demo mode.

## 4. Design system (foundation first)

**Tokens (CSS custom properties)**
- Colour: neutral scale (10 steps), one brand primary, plus semantic tokens for success, warning, danger and info.
- Attendance status tokens: `--status-present`, `--status-absent`, `--status-late`, `--status-excused`. Each has a background, a foreground and a border, in both light and dark themes.
- Grade tokens for A, B, C, S and F in the same way.
- Spacing on a 4px scale, radius scale (4, 8, 12, 16), and three elevation levels.
- Type scale: Outfit for headings and numbers, Inter for UI text. Use tabular numerals for marks and percentages.
- Motion: 120 to 200ms ease-out, with a `prefers-reduced-motion` fallback.

**Rules**
- Never rely on colour alone. Every status carries a letter and an icon (P, A, L, E, with a check, cross, clock or shield).
- Minimum touch target of 44px, and 48px in the attendance register.
- WCAG AA contrast in both themes.

**Core components to build and document**
Button (primary, secondary, ghost, danger), icon button, input, select, search field, segmented control, checkbox and switch, badge and status chip, avatar with initials, card, stat tile, progress ring, data table, tabs, modal, bottom sheet (mobile), toast with undo, empty state, skeleton loader, banner, breadcrumb, stepper (for imports), and print layout primitives.

Put these in `client/src/ui/` with one CSS file per component and a simple `/design-system` preview page in dev mode. Storybook is optional. A preview route is lighter and enough for a vanilla-CSS project.

## 5. Information architecture and navigation

- **Desktop:** collapsible left sidebar with Dashboard, Attendance, Students, Marks, Reports and Admin (admin only), plus a top bar with global search, sync status chip, theme toggle and user menu.
- **Mobile:** bottom tab bar with 4 items (Home, Attendance, Marks, Students). Admin and settings go under a "More" tab.
- **Role-aware menu:** hide what the user can't access instead of showing disabled items.
- **Command palette (Ctrl/Cmd+K):** jump to a student by name or admission number, or to a class register.
- **Sync status chip** sits in the global header at all times (see section 7).

## 6. Screen-by-screen redesign

### Login
- Clean split layout with school branding.
- Show the demo accounts as a collapsible "Demo mode" panel, controlled by an env flag, so it never appears in production.
- Clear error states, a show/hide password toggle, and a visible offline message.

### Dashboard (role-based)
- **Teacher:** "My classes today" cards, each with a register status (Not taken, Draft, Saved, Pending sync) and a single large "Take attendance" button. Below that, marks entries due.
- **Admin:**
  - Today's attendance as a Grades 6–13 by class grid, showing each class's percentage and flagging unmarked registers.
  - An "Absent follow-up" shortcut to the guardian phone list.
  - Recent audit events.
  - Stat tiles: enrolled, present today, absent today, registers outstanding.

### Attendance register (most important screen)
- **Header:** class, date, and a live counter bar (Enrolled, P, A, L, E, %) that stays sticky.
- **Rows:** big student rows with a photo or initials, calling name, and a 4-way segmented control. Default state is unmarked, with "Mark all present" as the primary bulk action.
- **Speed features:** tap a row's status to set it, long-press or an expand arrow to add a remark, and a jump-to-first-unmarked button.
- **Feedback:** subtle row tint per status, a small haptic or animation on tap, and an undo toast on bulk actions.
- **Submit:** a confirmation sheet showing the summary ("38 present, 2 absent") and a warning if anyone is still unmarked.
- **Duplicate prevention:** if a register already exists for that day, open it in view or edit mode instead of an error.
- **Reports** (tabs): daily summary table, absent phone directory (tap to call, copy number), and a monthly Student × Day matrix with sticky first column and a frozen header, color-coded and exportable.

### Students
- **List:** a searchable, filterable table on desktop, switching to cards on mobile. Filter chips for Grade, Class and Status are removable and persist.
- **Profile:** hero header (name, admission number, class, status), then tabs for Overview, Guardian, Attendance and Marks. The attendance ring and marks trend sit on Overview.
- **Add/Edit:** sectioned form with inline validation and autosave drafts.
- **CSV import:** a 4-step stepper (Upload, Map columns, Preview with errors highlighted, Confirm). Duplicates are flagged row by row, with a downloadable error report.

### Marks
- **Setup picker:** Term, then Class, then Subject, as a breadcrumb-style selector that remembers the last choice.
- **Entry grid:**
  - Spreadsheet-style with sticky header and sticky student column.
  - Arrow and Enter navigation.
  - Inline 0–100 validation with an error tooltip.
  - AB and Medical Exempt via a quick shortcut or dropdown.
  - Grade chip appears instantly as you type.
  - Paste from Excel support.
  - Autosave indicator, so no unsaved-data fear.
- **Mobile mode:** one student per card with a large numeric keypad and next/previous, since a wide grid doesn't work on phones.
- **Stats panel:** average, highest, lowest, pass rate and grade distribution as a small bar chart.

### Report card (print)
- Dedicated print stylesheet for A4 with fixed margins and no page-break surprises.
- Live preview with a letterhead settings panel (logo, school name, address).
- Batch print for a whole class, and signature lines kept at the bottom.

### Admin
- **Users:** table with role chips, assignment drawer (classes and subjects), and a reset-password dialog.
- **Backup and restore:** move into a separate "Data & safety" section with a danger-zone style. Restore needs type-to-confirm, and demo reset is hidden outside demo mode.
- **Audit trail:** filters by user, action and date, with an expandable row for details.

## 7. Cross-cutting UX

**Offline and sync (key differentiator)**
- Persistent chip in the header with states: Online, Offline, Syncing, and "3 pending".
- Clicking the chip opens a drawer listing queued items with timestamps, a "Sync now" button and a retry on failure.
- Each register card shows its own state: Saved on device, Syncing, Synced.
- Conflict resolution gets a clear side-by-side dialog (yours vs server).

**States:** every screen needs designed loading skeletons, empty states with a clear next action, and friendly errors with a retry.

**Forms:** labels always visible, inline validation on blur, helper text, and unsaved-changes guard.

**Accessibility:** full keyboard path, focus rings, ARIA for the segmented controls and grid, screen-reader announcements for sync changes, and sensible heading order.

**i18n readiness:** Sri Lankan schools often need Sinhala and Tamil alongside English. Even if you ship English only, avoid hard-coded strings and allow for longer text and different fonts.

**Responsive breakpoints:** 360 (small phone), 768 (tablet), 1024 and 1440 (desktop).

**Performance:** route-level code splitting, virtualised long lists, and optimistic UI for attendance taps.

**PWA:** add an install prompt, and a clear "update available" banner when the service worker updates.

## 8. Implementation roadmap

| Phase | Work | Rough time |
|---|---|---|
| 0. Discovery | Screenshot every screen, write the problems list, and watch 2–3 real teachers take attendance and enter marks | 2–3 days |
| 1. Foundation | Tokens, themes, typography, core components, preview page | 1 week |
| 2. Shell | Layout, responsive nav, global header with sync chip, login | 3–4 days |
| 3. Attendance | Register, offline UX, reports | 1–1.5 weeks |
| 4. Students | List, profile, forms, CSV import stepper | 1 week |
| 5. Marks and report card | Grid, mobile mode, stats, print layout | 1–1.5 weeks |
| 6. Admin and dashboard | Role-based dashboards, users, safety zone, audit | 1 week |
| 7. Polish and QA | Accessibility pass, device testing, visual QA, performance | 3–5 days |

Do wireframes for the Attendance and Marks screens first, as low-fidelity mocks, before touching code.

## 9. How to know it worked

- Attendance for a 40-student class in under 90 seconds, tested on a real phone.
- Zero lost registers across an offline-to-online test.
- Marks entry for one class faster than before, measured with a stopwatch.
- Lighthouse accessibility score of 95 or higher, and AA contrast in both themes.
- All touch targets 44px or larger.

## 10. Decisions you need to make

1. Mobile-first or desktop-first? I'd suggest mobile-first for teachers, with admin desktop-first.
2. Keep vanilla CSS, or move to CSS modules or Tailwind? Vanilla CSS with tokens is fine and avoids a big migration.
3. Which languages, if any, besides English?
4. Does the school need its own branding and letterhead, or is one default enough?
