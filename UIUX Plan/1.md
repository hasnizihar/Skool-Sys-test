Project: [hasnizihar/Skool-Sys-test](https://github.com/hasnizihar/Skool-Sys-test?utm_source=chatgpt.com) | School Management System | UI/UX Redesign v2.0

Your SkoolSys project already has a substantial MVP, so I recommend redesigning the existing application rather than rebuilding it from scratch.

The goal should be to transform SkoolSys into a polished, fast, accessible, and genuinely practical school management platform that teachers and administrators can use every day, including on unreliable school networks.

Based on the repository README, your existing system includes student management, offline attendance, marks management, printable report cards, administration, role-based access, and audit logs. It uses React 19, TypeScript, Vite, and a custom CSS design system.&#x20;

### Typography

Use a maximum of two font families, preferably one for the entire product.

- Inter: Primary UI typography, tables, labels, inputs, and numbers.
- Outfit: Optional for major headings and product identity.

Suggested typography scale:

| Element         | Size    | Weight  |
| --------------- | ------- | ------- |
| Page title      | 26–30px | 650–700 |
| Section heading | 18–20px | 600     |
| Card title      | 15–16px | 600     |
| Body            | 14px    | 400–500 |
| Table content   | 13–14px | 400–500 |
| Helper text     | 12–13px | 400     |
| KPI numbers     | 28–34px | 650–700 |

Avoid excessive shadows, gradients, animation, and oversized cards. This is a data-heavy application.

Role-aware navigation

#### Attendance UX requirements

The real implementation should have:

- Sticky class/date header and sticky submission controls.
- Clear unsaved, saved locally, syncing, synced, and failed states.
- One-tap attendance marking with large touch targets.
- Bulk marking with a confirmation or undo mechanism.
- Student-level remarks without leaving the register.
- Search within large classes.
- An explicit review step before final submission.
- Conflict handling if the same register is changed on multiple devices.

Critical: Offline saved does not mean server submitted. These states must be visually distinct.

### Screen 08: Examination and report cards

The examination area should provide a clear hierarchy:

`Academic Year → Term → Examination → Class → Subject → Marks`

Separate examination setup from marks entry.

The printable report card needs its own print stylesheet, A4 layout, school identity, student details, marks, grading legend, attendance, and signature areas.

Do not make the printable report card a screenshot of the dashboard. It should be a proper document layout.

### Screen 09: Reports and analytics

Build a consistent reporting interface with shared filters for academic year, grade, class, and date or term.

Proposed report views include daily attendance, monthly attendance matrix, absent-student follow-up directory, class performance, subject performance, and student examination history.

Use charts only when they clarify trends. Every report should have clear export and print options appropriate to its data.

### Screen 10: Staff, settings, and administration

Organize administrative functions into clearly separated sections: Users and Roles, Teacher Assignments, Academic Structure, School Profile, Data Management, and Audit Logs.

High-risk actions such as restoring a database, resetting demo data, or modifying access permissions need explicit confirmation, permission checks, and clear consequences.

## 10. AI coding workflow using Antigravity

For this project, avoid telling Antigravity to "redesign the whole app" in a single prompt. That often produces visually inconsistent pages and unintended functional changes.

Use this sequence:

Agent 1: Repository auditor

Inspect existing routes, components, styles, role permissions, offline behavior, and API dependencies. Produce an evidence-based audit.

Agent 2: Design-system architect

Define the tokens, component library, layout templates, and interaction patterns.

Agent 3: Frontend implementer

Redesign one module at a time, reusing the shared system and preserving backend contracts.

Agent 4: UX and regression reviewer

Check consistency, accessibility, role restrictions, mobile layouts, and existing workflows.

## 11. How to measure redesign success

The project should have measurable usability goals, not only improved screenshots.

| Metric                        | Suggested target                               |
| ----------------------------- | ---------------------------------------------- |
| Teacher attendance completion | Under 2 minutes for a typical class of 40      |
| Student lookup                | Under 10 seconds for a known student           |
| Marks entry                   | Efficient keyboard-only completion             |
| Critical UI accessibility     | WCAG 2.2 AA target                             |
| Mobile attendance             | No horizontal scrolling                        |
| Offline save feedback         | Immediate, unambiguous confirmation            |
| Navigation                    | Core tasks reachable in 1–3 navigation actions |
| Functional regressions        | Zero critical regressions before pilot         |

Validate these through actual user testing. They are targets, not current measured performance.
